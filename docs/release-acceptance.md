## Sequence and rollback

1. Confirm the production branch and record the last published Netlify deploy ID, the current `main` SHA, the current function settings and the deployed GA4 stream. Have the hosting owner confirm the publish control so a merge cannot publish an intermediate release unexpectedly.
2. Complete preview gates and record the exact PR #125 SHA that passed. Obtain explicit owner approval before merging or enabling production delivery and storage. If automatic publishing would publish two intermediate versions, use Netlify's publish control to hold the approved production deploy until the full stack is ready.
3. Merge #124 to `main` first. Keep its branch until #125 is retargeted to `main`. Refresh #125 against current `main`. If #124 was squash-merged, replay only #125 commits onto `main` and verify the resulting diff and all checks before merging #125. Review any changed SHA before publication.
4. Apply the production environment scope, enable the matching authorized provider webhook, publish the combined release and run read-only production smoke tests. With the owner's approval use labeled QA controls for the actual mobile or desktop intake, inbox, storage, acknowledgments and GA4. Exclude these from business metrics.
5. On broken intake, missing notifications, unexpected data exposure or misrouting, restore the recorded successful Netlify deploy and stop further automatic publishing until addressed. Roll back code on `main`, restore the previous function configuration if needed, and preserve the ledger, inbox and provider histories. Reconcile all accepted and pending requests from the rollback interval before retrying delivery.
6. Keep the holiday campaign approval and final owner proof in #114. The production release and transactional QA do not authorize any bulk campaign.
